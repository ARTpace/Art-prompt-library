# 风格包数据与分类规范 v1.1（建议稿）

日期：2026-11-01。分类字典：[详细分类表](style-pack-taxonomy-v1.md)。

## 1. 状态与范围

本规范是独立提示词仓库的分类与发布基线。`packs/` 保存已发布平台包，采集与分类工具在本仓库运行，工作数据和缓存默认不提交。本文涉及 Art Canvas 用户目录、合并与界面的部分是消费者兼容约定，不要求本仓库拥有主工具源码。

当前已支持：`pack.json`、按大类拆分的 JSON、`categories → subcategories → presets` 嵌套数据、按 ID 合并、用户增量层。系统提示词库读取相同的合并数据。

待实现：完整分类字典校验、跨包分类冲突报告、结构化来源展示与筛选、标签筛选、审核信息管理、全库分类迁移。不能因为文件写了这些字段，就认为程序已经会展示或严格验证。

适用对象为图片生成风格和任务模板。画师库、角色库保留各自内容包结构，不转换成风格包；它们可以共享界面组件，但不共用同一种数据格式。

## 2. 三种信息分开保存

| 信息 | 回答的问题 | 保存位置 |
|---|---|---|
| 主分类 | 这条主要用于什么生成任务？ | 所在大类、子类的嵌套路径 |
| 标签 | 有哪些可交叉筛选的特征？ | 条目 `tags`，建议新增字段 |
| 来源 | 从哪里收录、属于哪个系列？ | 条目 `source`，建议新增字段；保留现有 `description` 兼容 |

每条仅在一个主大类、主子类路径存储一次；可通过 `classification.subcategories` 关联同一大类下多个子类。不要在正文中解析分类，也不要在标题中硬塞分类前缀。禁止通过每次打开界面临时猜分类作为正式数据源。

## 3. 包目录与文件布局

```text
example-photo-pack/
  pack.json
  photography.json
  commercial.json
```

一个包可以包含多个大类。默认一个大类一个 JSON，文件名与大类 ID 对齐。不要为了来源平台新建大类；不同来源包可以包含同一标准大类和子类。

当前路径：内置包在项目 `data/style-packs/<packId>/`；用户安装包在用户数据目录 `style-packs/<packId>/`；用户改动保存在 `data/style-overlay.json` 增量层。管理界面负责导入、安装、导出和卸载，不手动把用户包写入内置目录。

JSON 使用 UTF-8、合法 JSON 语法，不带注释，不依赖字段排列顺序。分类与子类的显示顺序按清单顺序、内容数组顺序约定处理；当前子类没有独立的排序解析逻辑，不能只填一个 `order` 字段就假定已生效。

## 4. 清单示例

```json
{
  "schema": 1,
  "kind": "styles",
  "packId": "example-photo-pack",
  "name": "摄影精选示例包",
  "version": "1.0.0",
  "dataVersion": "2026-11-01",
  "author": "作者名称",
  "description": "人物与静物摄影模板",
  "taxonomyVersion": "1.1.0",
  "order": 500,
  "entryCount": 2,
  "categories": [
    {"id": "photography", "name": "摄影", "file": "photography.json", "order": 10}
  ]
}
```

| 字段 | 目标要求 | 说明 |
|---|---|---|
| `schema` | 必填，当前值为 `1` | 包结构版本，不能与分类版本混用 |
| `kind` | 必填，`styles` | 明确包类型 |
| `packId` | 必填、稳定且全局唯一 | 使用安全英文 ID，遵守现有导入器限制 |
| `name` | 必填 | 包的展示名称，可含来源名，不影响内容分类 |
| `version` | 必填 | 包发布版本，采用语义版本格式 |
| `dataVersion` | 建议填写 | 数据整理批次，不替代包版本 |
| `taxonomyVersion` | 目标新增，必填 | 当前解析器不会验证该字段，后续校验器读取 |
| `entryCount` | 发布时必填 | 包内实际条目数，不是合并后全库数量 |
| `categories` | 必填且非空 | 每个 ID 在同一清单只出现一次，对应文件必须存在 |
| `author`、`description`、`order` | 建议填写 | 包说明与顺序，不承载条目主分类 |

不能擅自提高 `schema` 为 2：新增分类规则不等于现有程序已经支持新包格式。

## 5. 分类文件与条目示例

以下 `photography.json` 与清单的 `entryCount: 2` 对应。分类归属以嵌套位置为权威，不再重复存一组容易冲突的 `category_id`、`subcategory_id`。

```json
{
  "categories": [
    {
      "id": "photography",
      "name": "摄影",
      "subcategories": [
        {
          "id": "photography_portrait",
          "name": "人物肖像",
          "presets": [
            {
              "id": "example_photo_window_portrait",
              "name": "窗边自然光人像",
              "prompt": "Portrait by a window, soft natural light, realistic skin texture.",
              "negative_prompt": "",
              "thumbnail": "https://example.com/previews/window-portrait.webp",
              "description": "自建示例",
              "tags": ["medium:photo", "subject:person", "lighting:natural"],
              "source": {
                "provider": "self",
                "collection": "摄影精选",
                "external_id": "window-portrait",
                "url": ""
              },
              "classification": {
                "taxonomy_version": "1.1.0",
                "method": "manual",
                "status": "reviewed",
                "reason": "核心任务是人物肖像摄影"
              }
            }
          ]
        },
        {
          "id": "photography_product",
          "name": "产品静物",
          "presets": [
            {
              "id": "example_photo_bottle_studio",
              "name": "玻璃瓶棚拍",
              "prompt": "Studio product photograph of a glass bottle on a neutral background.",
              "negative_prompt": "",
              "thumbnail": "",
              "description": "自建示例",
              "tags": ["medium:photo", "subject:object", "lighting:studio"]
            }
          ]
        }
      ]
    }
  ]
}
```

示例图片 URL 仅说明字段格式，不是真实素材地址，不能直接作为可用内容发布。

### 条目字段约束

| 字段 | 目标要求 | 兼容说明 |
|---|---|---|
| `id` | 必填，全库稳定唯一 | 已有 ID 不变，不随分类、标题、来源重命名 |
| `name` | 必填，非空 | 简洁表达主体与主要效果，避免纯广告词 |
| `prompt` | 必填，非空 | 完整可用的原始提示词，不在迁移中擅自改写 |
| `negative_prompt` | 可选字符串 | 没有就用空串，不伪造负面提示词 |
| `thumbnail` | 可选字符串 | 原图或预览地址，沿用当前程序可解析的形式 |
| `description` | 兼容保留 | 当前来源筛选读取该字段，结构化来源接入前不能删掉或突然改变含义 |
| `tags` | 目标新增，字符串数组 | 使用分类表字典，去重；当前列表尚未提供此字段筛选 |
| `source` | 目标新增，对象 | 分开保存平台、系列、原 ID、出处，不拿它充当主分类 |
| `classification` | 目标新增，对象 | 保存分类版本、方法、审核状态和理由；不是现有导入器的强制字段 |

新条目 ID 建议使用来源稳定前缀与上游 ID，例如 `provider_native123`。上游没有 ID 时，由首次导入生成并长期保存 UUID；不能每次分类重新生成，也不要只用标题作为 ID。

`classification.method` 建议值：`manual`、`assisted`、`rules`、`legacy`。其中 `rules` 表示纯本地规则匹配，不是 AI 或人工审核。`status` 建议值：`suggested`、`reviewed`、`needs_review`。机器建议不得直接标 `reviewed`；人工审核确认后才可变更状态。

v1.1 增加可选 `classification.stage`（`title` / `content`）和 `classification.resolution`（`resolved` / `category_only` / `unresolved`），分别记录证据阶段和分类完成程度，与人工审核状态独立。`resolved` 不代表已人工审核。批次报告还需记录 `title_hash`、`prompt_hash`、`taxonomy_version`、`rules_version` 供缓存续跑使用；当前应用不会自动执行这些阶段和缓存规则。

## 6. 归类判断流程

当前用户要求：只根据标题分类，不使用提示词正文、负向词、原分类、来源描述或图片补充推断。正文仅原样保存并进行完整性校验。

1. 全量遍历输入，按标题的主要任务与交付物判断，规则明确结果仍是建议。
2. 大类明确时保留标题明确匹配的全部子类，按已有优先关系选择主子类存储；不因多个子类命中而判为冲突。没有明确子类时归该类 `_pending`；标题含糊、缺失或跨大类冲突时归全局待分类。
3. 待处理队列只提供标题给 AI；标题不足时继续保留 pending，不读取正文强行提高覆盖率。
4. 历史正文分类在仅标题模式下重新判断，不以原结果作为证据；只保留明确记录为标题审核的人工分类，保留原包用于追溯。
5. ID、完整正文与所有非分类字段不变。多轮运行只复用匹配当前标题规则与模式的缓存，不能按相同正文传播分类。
6. 新子类先更新统一字典，不允许来源包自行创建同义分类。逐项核对结果和报告，不能将规则建议标为人工审核。

## 7. 导入与发布校验目标

现有导入器具有包结构及路径等基础检查，下表是待补齐的完整验收标准，不宣称已经全部实现。

| 层级 | 检查项 | 处理 |
|---|---|---|
| 安全 | ZIP 路径穿越、不安全文件名、超限大小、损坏 JSON | 拒绝导入；沿用现有安全边界 |
| 结构 | 清单缺失、包类型错误、分类文件缺失或清单与内容不一致 | 拒绝并列出文件与字段 |
| 分类 | 未知大类、未知子类、子类不属于父类 | 严格发布拒绝；旧包迁移模式进入隔离整理流程，不静默猜测 |
| 内容 | ID、名称、正文缺失或类型错误 | 拒绝对应包，提供条目定位 |
| 重复 | 同包同 ID 多次出现，包括跨分类重复 | 拒绝，不能依赖最后加载覆盖 |
| 跨包冲突 | 同 ID 被放进不同分类，或同 ID 的正文不一致 | 输出冲突报告；显式处理后再发布，不静默移动或覆盖 |
| 标签 | 未登记值、重复值、值类型错误 | 重复可规范化；未知值提示审核，不自动扩充全局词典 |
| 计数 | `entryCount` 与实际不符 | 发布拒绝；重算并修正清单，不影响原文件备份 |
| 媒体 | 无缩略图或远程图片暂时不可访问 | 警告，使用占位；不因网络瞬时失败删除条目 |
| 待分类 | 存在有效但待审核条目 | 允许整理版导入，展示待分类数量；不能伪装成已审核完整版 |

老包没有 `taxonomyVersion` 时认定为旧格式内容，不直接判定数据无效。提供迁移报告和整理预览，再由独立的迁移动作生成新版包；本次不实施该动作。

## 8. 去重、覆盖与数量口径

现有程序按分类、子类及条目 ID 进行合并，同 ID 在不同子类下可能重复出现；不能把当前合并行为称为全库严格去重。目标校验必须额外建立全局 `条目 ID → 所在路径` 索引。

新规范要求同 ID 只有一个有效分类位置。相同 ID、内容相同的跨包副本可复用；内容有差异时保留来源和冲突记录，由明确的更新规则决定，而不是靠包名排序解决。

不同 ID 但正文相同只算“疑似重复”，不得自动删除。去重和重分类分开处理，避免为了整理分类丢失有效变体。

| 数量 | 定义 |
|---|---|
| 包条目数 | 包内实际条目数量，与清单 `entryCount` 核对 |
| 安装总数 | 各包声明数之和，可能含重复，不等于可见总数 |
| 合并有效数 | 按当前合并规则及用户增量层得到的条目数 |
| 分类数 | 当前有效条目在所属大类、子类中的数量 |
| 筛选命中数 | 应用子类、关键词、来源等条件后的数量 |
| 已审核数 | 有真实审核记录且通过审核的条目数 |

界面默认展示合并有效数；大类计数等于其全部子类计数之和；筛选命中数不反过来修改分类静态总数。用户删除和修改仍遵守增量层逻辑。

## 9. 旧包迁移与回滚流程

1. **盘点与备份**：保存每个包、清单和用户增量层的原始副本；记录条目 ID、正文摘要、原分类路径、包版本和数量。
2. **固定分类版本**：使用本分类表 v1.1，不在同一批次中临时更改字典含义。
3. **形成建议表**：逐条记录原分类、目标分类、标签、建议理由和审核状态；来源型分类拆成来源字段。
4. **审核冲突**：优先处理摄影、综合、来源型分类以及跨包同 ID 冲突。含糊项保留待分类。
5. **生成新版包**：重组分类文件与清单，不修改原包；大类排序统一，条目 ID 保持不变。
6. **同步迁移增量层**：新增条目的路径必须更新，基于 ID 的修改和删除记录要逐项验证，不能遗漏用户自建内容。
7. **核对内容**：以 ID 多重集合与正文摘要核对无丢失、无意外重复；所有例外写入报告。只比较总数相同不算通过。
8. **检查引用**：验证收藏、缩略图、详情、搜索、来源筛选和生成界面引用；确认大类与全库唯一条目数准确，子类按关联计数且允许重叠。
9. **可回滚发布**：只有完成预览和验收后才替换安装包与对应增量层；回滚时恢复两者，不能只恢复某个 JSON。
10. **关闭临时猜测**：标准子分类覆盖后移除摄影按标题推断的展示兜底，分类全部来自文件。

拆分或合并条目是单独的数据变更：保留原 ID、派生 ID 与替代关系，明确引用迁移方法，不能夹带在普通分类迁移中静默完成。

## 10. 界面与缓存要求

- 左侧只显示标准大类；卡片区顶部显示当前大类的子类标签和计数，包含“全部子分类”。
- 搜索、来源、收藏、子分类可组合筛选，分页请求必须包含完整筛选条件。
- 切换大类时清除旧子类；同名子类不能跨大类串用。
- 卡片底部显示标题，点击详情查看完整提示词；分类筛选不触发每张卡片重新推断归属。
- 风格包、用户增量层变化时刷新目录缓存和分页缓存，并更新总数、分类标签与来源。
- 大数据量按页加载，不将整库卡片一次插入页面。

## 11. 版本管理与交付清单

包版本、结构版本、分类版本分别管理。增加兼容性子类升级分类次版本；改变既有归属含义或删除分类需要迁移方案与主版本调整；修正文案或解释升级修订版本。旧 ID 可废弃并提供映射，但不得分配给新含义。

每次整理应交付：

- 新版包及修正后的清单。
- 使用的分类表版本。
- 原分类到新分类映射表。
- 逐条审核记录、待分类列表及跨包冲突报告。
- 分类前后计数与正文完整性核对结果。
- 用户增量层兼容性说明及回滚备份位置。

## 12. 建议实施顺序

先确认分类表和边界，再做只读盘点与建议报告；首批整理摄影和综合，验证后整理其余来源包。最后接入完整校验和标签筛选，并移除临时关键词分组。不要先批量修改全部已安装文件再补规则。

## 多子类关联（schema 1 兼容扩展）

保持原始记录的一份正文和 ID，嵌套路径是兼容旧消费者的主分类。额外匹配存为：

```json
{"classification":{"stage":"title","subcategories":[{"id":"photography_portrait","name":"人物肖像"},{"id":"photography_fashion","name":"时尚摄影"}]}}
```

数组须非空、包含主子类、无重复 ID，全部属于主大类且来自分类字典；不能同时混入 pending 和已明确子类。各子类都能筛到同一条记录。「全部」和大类数量按唯一 ID 计数，子类计数允许重叠，不能相加当全库条目数。旧包没有该字段时仅按嵌套主子类处理。大类冲突仍保留待分类，不据正文推断关联。
